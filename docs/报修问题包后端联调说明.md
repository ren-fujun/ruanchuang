# 报修问题包后端联调说明

本说明仅描述当前演示后端的接口，不代表学校已批准业务流程或已经连接真实部门。现有 JSON 存储和演示登录不适合真实学生数据。

## 数据准备

问题包接口要求辅导员用户配置由可信管理方维护的 `studentIds` 数组；未配置或未包含工单学生时拒绝。新建的虚构演示数据已配置示例范围和后勤接收人，已有数据文件不会自动变更。接收人必须是现有 `logistics` 角色用户。账号创建、范围维护和正式鉴权尚未实现，不允许由客户端自行提供或修改角色与范围。

## 接口顺序

- `POST /api/issue-bundles`：辅导员提交 `ticketIds`、可选 `note`；只产生草稿。
- `GET /api/issue-bundles`：辅导员查询本人、且仍在授权学生范围内的包。
- `PATCH /api/issue-bundles/:id`：修改草稿工单或备注；`POST /api/issue-bundles/:id/cancel` 取消草稿。
- `POST /api/issue-bundles/:id/dispatch`：请求体 `recipientId` 为后勤用户 ID；重新核验所有工单状态与授权范围。转交只意味着系统内指定接收人，不代表对方已接收。
- `GET /api/logistics/work-orders`：后勤只能查询分派给自己的事项，返回必要问题字段，不返回内部备注。
- `POST /api/logistics/work-orders/:bundleId/:ticketId`：后勤使用 `{ "action":"accept" }` 接收单条；随后以 `{ "action":"resolve", "result":"处理结果" }` 提交该条结果，进入学生待确认状态。
- `POST /api/tickets/:id/reopen`：学生对本人待确认事项提交 `{ "reason":"未解决原因" }`；辅导员可通过 `POST /api/issue-bundles/:bundleId/:ticketId/redispatch` 核对并重新转交，后勤重新接收处理。学生满意使用现有 `/api/tickets/:id/confirm`。

每条工单独立处理，问题包保留各次操作历史；后勤可退回单项，由辅导员核对后再次转交。当前没有问题包自动结案、主动消息推送、转交其他部门、真实文件上传或学校系统对接。旧工单详情与操作已加入学生负责范围检查，但其他数据域仍须逐项检查。当前保存在内存并由 JSON 文件异步落盘，不具备生产事务、并发和备份保障。
