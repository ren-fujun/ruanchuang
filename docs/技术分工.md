# 智汇中枢 · 四人技术分工

> 适用范围：当前阶段只做技术，不做 PPT / 视频 / 路演材料。
> 目标：把“学生提交 → AI 预检 → 辅导员审核分派 → 部门处置代录 → 学生确认评价 → 数据归档”做成稳定、可测试、可演示的工程版本。

---

## 一、分工总览

采用 **1 后端 + 2 前端 + 1 AI/质量工程** 的结构，四个人都写代码，每人都对自己的模块质量负责。

| 成员 | 技术角色 | 主责模块 | 不负责 |
| --- | --- | --- | --- |
| **A** | 技术负责人 / 后端与架构 | API 契约、认证与权限、工单状态机、SLA、通知、统计接口、代码集成 | 不日常改学生端/辅导员端页面 |
| **B** | 学生端 / 设计系统 | 学生端全部页面、登录页、共享 UI、设计令牌、响应式与可访问性 | 不直接改辅导员端业务页面 |
| **C** | 辅导员端 / 数据可视化 | 辅导员全部页面、中枢看板、分派/督办/拆分、洞察图表 | 不改后端状态机与 AI 规则 |
| **D** | AI / 测试与交付工程 | AI 分类与风险、知识库检索、模型增强与降级、E2E/接口测试、部署与种子数据 | 不直接重构前端页面 |

### 为什么这样分

- 学生端和辅导员端都有大量页面与交互，各给一个 owner，避免一个人前后端全包；
- 后端与状态机是业务正确性的核心，必须有一个固定 owner；
- AI 与测试放在同一个人身上，形成“改规则 → 跑评测 → 回归”的闭环；
- 不设“纯打杂”角色，D 的产出直接影响技术可信度和发布质量。

| 目录 / 文件 | Owner | 说明 |
| --- | --- | --- |
| `server/index.js` | A | 路由、中间件、权限、工单流转、统计聚合 |
| `server/store.js` | A | 持久化与数据读写 |
| `server/ai.js` | D | 分类、风险、SLA、知识库检索 |
| `server/llm.js` | D | DeepSeek 增强、超时与降级 |
| `server/seed.js` | D | 部门、用户、工单、知识库演示数据 |
| `src/types.ts` | A | 前后端共享类型，改动必须通知全员 |
| `src/lib/api.ts` | A | API 客户端方法，B/C 只调用不私自改接口 |
| `src/App.tsx` / 路由 | A | 路由与角色守卫 |

| `src/components/layout/*` | B | 手机壳、底部导航、页头 |
| `src/components/TicketCard.tsx` | B | 双端共用工单卡片 |
| `src/pages/Login.tsx` | B | 登录与一键体验 |
| `src/pages/student/*` | B | 学生端页面 |
| `src/styles.css` / `styles-student.css` | B | 设计系统与学生端样式 |
| `src/pages/Messages.tsx` / `Profile.tsx` | B | 双端共享页面；C 提需求，B 改 |
| `src/pages/counselor/*` | C | 辅导员端页面 |
| `src/styles-counselor.css` | C | 辅导员端样式 |
| `scripts/*` | D | E2E、截图、数据重置 |
| `package.json` / `vite.config.ts` / `index.html` | A | 依赖与构建配置；D 提需求，A 改 |

### 三条硬规则

1. **A 是 API 契约唯一出口。** B/C 需要新字段时，先找 A 加，不允许前端自己拼假数据掩盖后端缺失。
2. **B 是共享 UI 唯一出口。** C 需要复用按钮、徽章、图表容器时，向 B 提 PR 或由 B 改，避免两套视觉。
3. **D 是 AI 输出唯一出口。** AI 返回结构变化必须同步 A 更新类型，并给 B/C 一份固定 fixture。

## 三、接口契约先行

技术并行最大的风险不是写不完，而是“前端等接口、后端等页面”。第一优先级是 A 在 **2 天内**产出轻量契约。

### 契约必须包含

- 每个接口的 method / path / 入参 / 出参示例；
- 错误结构统一为 `{ message: string }`；
- 工单状态枚举与允许的流转；
- `statusLabel`、`progress`、`minutesLeft`、`overdue` 由后端计算，前端不重复实现业务规则；
- 角色权限：学生只能看自己的工单，辅导员看全量；
- AI 预检返回：`analysis`、`knowledge`、`canSelfSolve`、`needsTicket`、`quickReplies`。

### 建议新增的契约文件

```text
docs/api-contract.md
docs/ticket-state-machine.md
docs/ai-eval.md
```

### 状态机（唯一版本）

```text
pending_review  待审核
  → assigned    已分派
  → processing  处理中
  → awaiting_confirm 待确认
  → completed   已办结

允许的例外：
- pending_review 可分派、可退回补充（本期可不做退回）
- assigned / processing 可催办、可加备注
- awaiting_confirm 可提醒学生确认，SLA 暂停
- completed 只允许评价，不再变更状态
```

> 所有状态变更必须经过后端校验；前端隐藏按钮不等于权限控制。

## 四、10 个工作日技术冲刺

> 如果比赛周期更短，把 Day 1–5 压缩成 3 天，Day 6–10 压缩成 3 天。

### Day 1–2：契约与基线

| 人 | 任务 | 交付 |
| --- | --- | --- |
| A | 写 API 契约、状态机文档；整理 `types.ts`；确认路由与权限中间件 | 契约文档、类型基线 |
| B | 360/390 双尺寸走查学生端；列 P0/P1；统一 loading/empty/error | 缺陷清单、共享组件清单 |
| C | 走查辅导员端主流程；列出需要的统计字段；确认分派/督办交互 | 页面问题清单、数据需求 |
| D | 建 30–50 条 AI 评测样例；跑当前分类/风险基线 | 评测集、基线报告 |

**Day 2 结束必须有一次 30 分钟对齐：** 谁能提供什么字段、什么时间提供。

### Day 3–4：核心链路并行

| 人 | 任务 | 交付 |
| --- | --- | --- |
| A | 登录/会话/RBAC；工单状态机守卫；SLA 与 overdue；通知事件 | 可测的后端核心 |
| B | 学生提交表单校验、AI 预检状态流转、提交成功页、进度页 | 学生端主链路可用 |
| C | 辅导员审核分派、部门接单/处置结果、催办、备注 | 辅导员主链路可用 |
| D | AI 规则修正、知识库匹配阈值、DeepSeek 超时降级 | AI 行为稳定 |

### Day 5：第一次集成

- 所有人停止新功能，跑 **一条完整链路**；
- D 跑 E2E，输出 P0/P1；
- A 只修后端阻塞，B/C 只修主流程阻塞；
- 目标：从学生提交到学生评价，无人工改数据。

### Day 6–8：补完与加固

| 人 | 任务 | 交付 |
| --- | --- | --- |
| A | 复合工单拆分、父子工单约束、审计字段、统计接口 | 后端功能完整 |
| B | 学生端附件、消息已读、评价、异常提示、空状态 | 学生端可交付 |
| C | 洞察图表真实数据、筛选与搜索、深链、拆分交互 | 辅导员端可交付 |
| D | E2E 扩展、权限测试、种子数据、部署脚本 | 测试与交付包 |

### Day 9：全量回归

- 学生端：提交、预检、进度、催办、确认、评价、消息；
- 辅导员端：审核、分派、接单、处置、催办、备注、拆分、提醒确认、洞察；
- 权限：学生访问他人工单、学生访问辅导员接口、无 token 访问；
- 兼容：360 / 390 / 桌面；
- 异常：空数据、重复提交、AI 超时、网络失败。

### Day 10：发布候选版

- 只修 P0；
- 打 tag：`v1.0-rc`；
- 产出 `README`、启动脚本、演示账号、重置数据说明；
- 冻结功能，进入下一阶段。

## 六、协作规则

### Git 流程

```text
main         可演示、可部署
feat/*       功能分支
fix/*        修复分支
```

- 不直接 push `main`；
- 每个 PR 至少 1 人 review；
- 服务端 PR 由 A review；
- 共享 UI PR 由 B review；
- AI 规则 PR 由 D 自测 + A 确认接口；
- 合并前必须自己跑一遍主流程。

### 每日 15 分钟站会

每人只回答：

1. 昨天完成了什么？
2. 今天最重要的一件事？
3. 现在卡在谁那里？

### 集成检查点

- **Day 5**：主链路必须打通；
- **Day 9**：全量回归；
- **Day 10**：功能冻结，只修 P0。

### 接口变更流程

1. A 更新 `types.ts` 与契约文档；
2. 群里发变更说明；
3. B/C 更新调用；
4. D 更新 E2E；
5. 合并。

### DoD（完成定义）

一个任务算完成，必须同时满足：

- [ ] 正常路径可用；
- [ ] 空数据/加载/错误路径可用；
- [ ] 360 / 390 不溢出；
- [ ] 权限正确；
- [ ] 无 console error；
- [ ] 有对应测试或手工验证记录；
- [ ] 不引入未约定接口。

## 十、如果四人技能不均衡

- **两个人偏后端**：A 做核心后端，D 做 AI + 测试；B 学生端 + 共享 UI，C 辅导员端 + 图表。
- **只有一个前端**：B 做双端页面与设计系统，C 转做数据可视化 + E2E + 接口测试；A/D 分担后端。
- **有人暂时不熟悉代码**：先安排“测试用例 + 数据准备 + 文档 + 小 bug 修复”，但必须在一个迭代内接手一个独立模块，避免长期边缘化。
- **有人明显更强**：强的人做架构与 review，不强的人做边界清晰的页面/测试，不要把全部关键路径压在一个人身上。
