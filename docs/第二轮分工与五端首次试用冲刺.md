## 1. 本轮依据与完成边界

本轮以辅导员老师最新五点意见、用户对请假及报修的补充为准。冲突的旧流程不再作为开发要求：报修不经辅导员前置审核；不满意不无限重开；学业跟进不按导师/辅导员写死工作职责。

用户明确：本科生选择辅导员批假；研究生选择班导师批假，两个不同路径。用户补充“加一个终止节点，学生提交不满意的结果之后再报给后行”；本文将“后行”按“后勤”理解，保留异议到达后勤的动作。后勤一次书面回应、辅导员协调结案的具体设计是本轮建议，需开工时快速核对，不当作学校已有规定。

交付要求：五个业务端可在同一试用部署中真实登录，报修直达、请假双路径、学业协商、双向监督均能操作；有独立账号、独立数据、反馈入口、HTTPS地址和二维码。未通过验收的模块不能靠静态页或Mock宣布完成。

## 3. 五点改动的统一产品口径

### 3.1 辅导员：电脑网页优先

主界面按1366×768和1440×900验证：固定侧栏、概览、可筛选表格、右侧详情或独立详情页。首页优先显示请假待批、超时未处理、报修异议、待协商学业任务；报修全部进度为只读查询。手机保留可用性，不让手机底部导航决定桌面布局。沿用现有低饱和风格，不在本轮全面换肤。

### 3.2 请假：本科生与研究生两条路径

- `educationLevel=undergraduate`：本人 → 选择所属范围内辅导员 → 同意/驳回 → 学生收到结果。
- `educationLevel=postgraduate`：本人 → 选择所属范围内班导师 → 同意/驳回 → 学生收到结果。
- 学生类型、候选审批人由服务器维护；学生只能从合法候选人中选择，不能改请求字段变更学历类型或选任意教师。
- 班导师可复用导师端登录，但要配置 `classAdvisor` 能力及对应学生范围；学业导师不自动获得研究生请假权限。一个老师可以兼任多种身份。
- 两条路径独立配置和测试，不添加未要求的多级审批。表单最少为开始/结束时间、原因和审批人；结束不得早于开始。审批必须校验待审批状态、本人权限和版本，重复点击只产生一次决定。
- 首轮支持提交、待批、同意、驳回、结果查看；撤销、更正、长假分级、销假和真实学校系统同步另排，不冒充已有规则。不能把预约页面当作请假完成。

### 3.3 报修：学生直达后勤

学生选择报修类型、地点、描述并确认提交后，服务器直接创建一条后勤待接单事项。后勤按预置校区/楼栋/责任范围接收，范围内人员领取时后端只允许一人成功。无人可接的事项明确显示“待后勤分配”，不能静默进入辅导员审核或提示已接单。

辅导员看自己负责学生的状态、等待时长、后勤计划和结果，可提醒、询问并记录协调。新报修不再出现“辅导员审核通过才派发”，不允许辅导员通过旧代录接口伪装后勤接单/完工。其他非报修事务保留各自已有受理规则，不能把所有诉求统一直派后勤。

### 3.4 学业预警：协商分工，权限仍有边界

教务创建名单后，对应辅导员与导师看到同一事项；初始为“待协商”。双方协商联系人、行动安排和下一步时间，系统记录发起人、被指定人确认/接受以及变更历史。任一方可承担联系、提醒或跟进，不硬编码“导师必须面谈、辅导员只能监督”。未协商事项应可见，不能丢失。

可灵活分工不等于任意访问：只允许关联学生的导师/辅导员参与；个人敏感记录按明确可见范围保存，协同摘要单独提供；教务仍负责正式学业结果来源和回写。两人同时认领用版本控制，不能重复生成两套任务。

### 3.5 双向监督：异议报后勤，有明确终止

建议状态链如下，字段名由A/D在开工前两小时冻结：

```text
学生报修 → 后勤待接单 → 后勤处理中 → 后勤一次提交处置结果 → 学生待反馈
    ├─ 满意 → 完成（终态）
    └─ 不满意并说明原因 → 异议送达后勤 + 辅导员可见
                           → 后勤补充说明 / 到期未回应标记
                           → 辅导员核对双方记录并协调
                           → 协调结案（终态，保留结论与后续安排）
```

“一次”指原工单不自动回到普通接单/维修流程；异议说明和协调不伪装成第二次维修成功。学生在待反馈阶段只能提出一次异议，允许补充证据但不无限开新一轮。原有 `reopen/redispatch` 对新版报修必须由后端拒绝，不能只隐藏按钮。历史记录保留；旧返工单在试用前冻结归档或明确迁移，不删除历史。

后勤实际未解决、需求超出服务范围、双方理解不同、证据不足都应能客观记录。“双向监督”不预设一定是谁不负责，也不让AI判责。辅导员协调结论包括事实、双方说明、后续动作、负责人和时间；协调结案不等于设备已修好。确需再次现场服务时，人工决定是否新建关联任务，记录关联原因；不自动重开原单，新任务不计入原单一次维修完成率。

超时提醒只增加待办/通知，不自动标为满意、不自动裁责。接单与异议回应阈值作为试用配置，不写成学校承诺。统计分别展示已修复、待反馈、待协调、协调结案，不能将“协调结案”混算成“维修成功”。

## 6. 接口和代码交接约束

本节是拟定契约，非已实现API。A在D1前2小时拍板命名，随后各人按统一契约实现，不再维护两套不兼容提案。

| 业务 | 服务主责 | 必须统一的契约 |
|---|---|---|
| 报修/异议 | D，A审查 | 创建唯一repairId；领取、结果、学生异议、后勤回应、辅导员提醒/协调结案；所有写操作带requestId与version；查询权限一致 |
| 请假 | B，A提供身份范围 | 候选审批人、申请、本人/待批列表、决定；educationLevel由服务端确定；审批人只能操作指向自己的待批单 |
| 学业 | B，A负责教务入口 | 同一AcademicCase ID；批次导入关联已有学生关系；协商/接受/变更及结果回写；C读取可见摘要 |
| 试用反馈 | A，C提供共享UI | 描述/类型/评分/页面路径；身份由会话取得；仅团队管理员查看全部反馈；不把反馈管理员权限给所有辅导员 |

错误口径：401会话无效，403越权，409版本/重复动作冲突，400字段不合法。接单、审批和结案在服务端执行原子校验；同一requestId重试不得增加第二条记录。统计以服务端实际状态为准。

优先把B请假、D后勤/监督拆成独立路由；只有A统一挂载server/index.js，避免四人在同一文件冲突。B复用server/b和apps/mentor；C主改src/features/c与学生/辅导员页面；D主改后勤模块、apps/logistics和部署脚本。共享类型由A统一发布。

旧问题包非本轮报修必经步骤：复用已有后勤单项模型，必要时内部兼容单条容器，但学生不用等辅导员建包。暂未接通的打包/预约增强在试用中隐藏或标注不可用，不允许前端假成功。
