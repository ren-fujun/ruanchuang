### 2.3 那条失败用例的定性

`test-notice-extract.mjs` 的唯一失败用例是**测试自身的 UTC 口径问题**，不是抽取逻辑错误：

```
FAIL 明天 + 中文数字时间
  时间: 2026-11-10 09:30  |  地点: 学院会议室      <- 抽取正确（本地日期 +1 天）
  断言: r.date === new Date(Date.now() + 86400000).toISOString().slice(0,10)
```

当本地时间已是 `2026-11-09` 凌晨时，`new Date(Date.now()+86400000).toISOString()` 仍落在 `2026-11-08T16:xxZ`，取 `slice(0,10)` 得到 `2026-11-08`。断言应按 Asia/Shanghai 本地日期计算，或与 `extractMeeting` 使用同一基准日。

## 3. 合并后仍对不上的差异（关键结论）

两个前端**都在等同一份 v1 契约**，而当前后端尚未实现它。根应用 `src/lib/http.ts` 与教师端 `src/lib/api.ts` 对同一件事的判定完全一致：

```ts
// 根应用 src/lib/http.ts
if (!payload || typeof payload.code !== 'number') {
  throw new ApiError('接口未按 v1 返回 {code,msg,data}，请先完成 envelope 包装。', 50001, response.status)
}
```

```ts
// 教师端 src/lib/api.ts
if (!res.ok || body.code !== 0) { throw new ApiError(body.msg || ..., body.code, res.status) }
return body.data as T
```

### 3.1 后端整体未做 envelope（阻塞全部接口）

运行时实测：`/api/health`、`/api/me`、`/api/departments`、`/api/tickets`、`/api/notifications` **一律返回裸 JSON**，没有任何 `{ code, msg, data }` 包装。

- 例：`/api/tickets` → `{"tickets":[...],"counts":{...}}`（无 `code`）
- 后果：两个前端在任何一次真实请求上都会立刻抛 `接口未按 v1 返回 {code,msg,data}`，页面进入错误态。

这**不是**本轮合并引入的缺陷，D 已在 `docs/联调记录.md` 记为 `待修`；本轮新增的证据是：**已实际启动服务并运行冒烟，确认为运行时事实**（该文档原先标注为"来自代码审查，未启动过后端"）。

### 3.2 教师端与后端的字段 / 路径对照

教师端按修订 PDF 实现，后端按现有实现，两者系统性不一致：

| 维度 | 现有后端（`/api/*`） | 教师端期望 | 是否冲突 |
| --- | --- | --- | --- |
| 工单列表 | `GET /api/tickets` | `GET /api/counselor/tickets` | 路径不同 |
| 工单详情 | `GET /api/tickets/:id` | `GET /api/counselor/tickets/{ticketId}` | 路径不同 |
| 工单主键 | `id`（如 `ZX20261107015`） | `ticketId` | 字段名不同 |
| 风险字段 | `risk` | `riskLevel` | 字段名不同 |
| 状态枚举 | 小写：`pending_review` / `assigned` / `processing` / `awaiting_confirm` / `completed` | 大写：`PENDING_REVIEW` / `ASSIGNED` / `PROCESSING` / `PENDING_CONFIRM` / `CONFIRMED` / `ARCHIVED` / `DRAFT` / `REJECTED` | 值域不同，且 **`awaiting_confirm` vs `PENDING_CONFIRM` 无自动映射** |
| 部门字典 | `GET /api/departments` | `GET /api/dicts/responsibility`（`{departments,categories}`） | 路径与结构不同 |
| 当前用户 | `GET /api/me` | `GET /auth/me` | 路径不同 |
| 分页 | 无 `page`/`pageSize`/`total`/`hasMore` | 需要 `{list,total,page,pageSize}` | 后端缺字段 |
| 教师端写操作 | 后端有 `review`/`progress`/`urge`/`note`/`split`/`remind-confirm`（`PATCH`/`POST` 混用） | 期望 `review`/`assign`/`split`/`urge`/`notes`/`remind-confirm`/`archive` | 后端**无** `assign`、`archive`；`note` vs `notes` 不同 |
| 权限 | 后端无 `permissions` 字段 | 教师端所有操作按钮只读 `permissions` | 后端缺字段 |
| 登录 | `POST /api/auth/login` → `{token,user}` | `POST /auth/login` → `{token,user}`，经 envelope | 仅 envelope 差异 |

**共用点（合并后已确认一致，是好消息）**：两端都用 `localStorage` 键 `zhihui_token` 存 token，且都用 `Authorization: Bearer <token>`。所以一旦 envelope 补齐，登录态可以互通，不需要迁移 token。

### 3.3 同端口冲突

教师端 `vite.config.ts` 与根应用**都占用 5180**，且教师端设了 `strictPort: true`（会直接启动失败而不是换端口）。两个应用不能同时启动。教师端 `README.md` 也提醒了这一点。
