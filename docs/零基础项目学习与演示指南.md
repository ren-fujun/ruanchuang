# 智汇中枢：零基础学习与演示指南

## 1. 先认识你手里的版本

这个项目是一个**演示原型**：学生提交诉求，辅导员查看、判断并记录跟进。系统里的部门、联系方式、学生和统计所依据的初始工单是演示数据，不能当作学校实际情况。现在没有接入学校部门系统：点击记录督办并不等于给部门发送消息；附件只保存名称、类型和大小，不保存附件内容。

明天可以请两位辅导员重点判断：学生是否需要自己提交、哪些情况辅导员真的会受理、平时通过什么渠道联系部门、处理时限如何确定、哪些字段必须记录。真实数据先不要填入演示系统，等明确授权、脱敏方式和存储方案后再处理。

## 2. 先理解三个基本概念

- **前端**：用户看到和点击的页面，主要在 `src/`。
- **后端**：接收请求、判断权限、处理工单和返回结果，主要在 `server/`。
- **数据**：当前默认保存到本机 JSON 文件 `server/data/store.json`；它不是 Git 上共享的实时数据库。实际位置可用环境变量 `ZHIHUI_DATA_FILE` 指定。

可以把流程想成：学生在前台填表 → 前台通过接口把内容交给办公室 → 办公室整理、记录 → 前台把结果展示出来。**接口**就是双方约定的通信方式，不是可视化页面。

## 3. 跟着一条诉求看代码

例子：学生说“图书馆二楼空调故障”。按下面顺序阅读，不需要一次全懂。

1. `src/pages/student/NewTicket.tsx`：学生填写描述、地点并点击预检或提交。`tsx` 表示 TypeScript 加页面结构。
2. `src/lib/api.ts`：把页面动作翻译为接口调用；`src/lib/http.ts` 负责发送请求、处理响应和错误。
3. `server/index.js`：找到对应接口，例如 `POST /api/ai/precheck` 和 `POST /api/tickets`。`POST` 可以理解为向后端提交内容。
4. `server/ai.js`：根据描述提出类别、风险、建议部门和需要补充的信息；这些只是建议。
5. `server/ai/knowledge.js`：搜索示例知识库；信息过少或有歧义时，不直接建议自助解决。
6. `server/llm.js`：如果配置了模型，尝试增强分析；不可用时回退规则。没有配置不代表接入了真实大模型。
7. `server/store.js`：加载和保存数据；`server/seed.js` 负责演示初始数据。
8. `src/pages/counselor/Home.tsx` 和 `TicketDetail.tsx`：辅导员查看待办、审核建议并记录进展。
9. 学生通过 `src/pages/student/TicketDetail.tsx` 查看进度并确认。内部备注不会显示给学生。

工单状态依次为 `pending_review`（待审核）→ `assigned`（已分派）→ `processing`（处理中）→ `awaiting_confirm`（待学生确认）→ `completed`（已办结）。是否符合真实工作流程需要向辅导员求证。

## 7. 看懂常见代码符号

- `const name = ...`：给一个值或函数取名字。
- `function` 或 `=>`：定义一段可以重复执行的操作。
- `if (...)`：条件成立时才执行后面的代码。
- `{ ... }`：可能表示一组代码，也可能表示一条包含多个字段的数据。
- `async` / `await`：等待接口或其他异步操作完成。
- `app.get(...)` / `app.post(...)`：注册后端读取 / 提交接口；`patch` 通常用于更新。
- React 页面里 `<button ...>` 表示按钮；`onClick` 后面的是点击时执行的函数。
- 测试里的 `assert.equal(实际, 期望)`：检查结果是否与预期相同。

## 8. 怎么提出清楚的修改建议

用四句话描述：①谁在什么页面；②做了什么；③现在发生什么；④希望发生什么。例如：“辅导员在工单详情点记录督办后，只看到成功提示。我希望页面同时显示‘请线下联系后勤’，避免误以为系统已发消息。”如果涉及学校真实流程，再补充来源、哪些规则已确认、哪些还不确定。

建议依次阅读第 3 节的文件，每次打开一个文件，先找接口名或按钮文字，再追踪它调用的函数；不理解某一行时，把文件名和代码片段发出来提问。
